## Context

The `windows-installer-cli-and-wsl-panel` change added the flow: GUI Configure → copy the static musl helper `crypt-env-setup` into the distro `/tmp` → run it → apply `cryptenv_setup::apply` (write `env.sh` + the rc marker block). The NSIS installer places `crypt-env.exe` next to `tauri-crypt-env.exe` and adds that folder to the Windows user `PATH`. WSL appends the Windows `PATH` by default, so `crypt-env.exe` already works inside WSL through interop. The Windows CLI talks to the vault on the Windows loopback, so it does not depend on WSL networking mode. See proposal.md → Why.

## Goals / Non-Goals

**Goals:**
- Configure makes `crypt-env` run the Windows CLI inside any distro, for any Windows user and install path.
- Keep a single implementation of the shell contract in the `cryptenv_setup` crate, used by both the GUI helper and the unit tests.
- Keep Configure/Remove non-destructive and reversible.

**Non-Goals:**
- Argument path translation, a native Linux binary, a second command name (see proposal Non-Goals).
- Making the launcher available to non-interactive login shells that never source `.bashrc`/`.zshrc` (see Risks).

## Decisions

### D1 — Launcher in a CryptEnv-owned directory, appended to PATH

The launcher is `~/.local/share/cryptenv/bin/crypt-env`. The managed `env.sh` gains an idempotent append:

```sh
case ":$PATH:" in *":$HOME/.local/share/cryptenv/bin:"*) ;; *) PATH="$PATH:$HOME/.local/share/cryptenv/bin" ;; esac
export PATH
```

- **Why an owned directory:** CryptEnv is the only thing that ever writes there, so a collision with a user's own `crypt-env` is practically impossible. Remove can safely delete the directory once it is empty.
- **Why append:** a native Linux `crypt-env` on `PATH` (for example in `~/.local/bin` or `~/.cargo/bin`) keeps winning, and the launcher is a fallback.
- **Rejected: `~/.local/bin/crypt-env`.** It is a shared directory, so the risk of clobbering a native build is real. Ubuntu's `~/.profile` also adds it to `PATH` only when the directory existed at login, which makes it unreliable on a first install.
- **Rejected: a shell alias or function in `env.sh`.** It only works in interactive shells. It is invisible to `command -v`, `xargs`, `make` and scripts, and does not work in `sh`.

### D2 — Windows CLI location: resolved by the GUI, translated by the helper

- **GUI:** `std::env::current_exe()?.parent()/crypt-env.exe`, checked to be an existing non-empty file. This is the installation performing the Configure, so it is correct for any user, drive or per-machine vs per-user install. There are no registry lookups and no `%LOCALAPPDATA%` guessing. If the file is missing, the helper is called without the argument and reports `skipped: windows CLI not found`.
- **Helper:** new `--windows-cli <WINPATH>` argument, translated with `wslpath -u` and falling back to `windows_path_to_wsl`, the same pattern as `--appdata`. Using the helper's in-distro translation honours custom `[automount] root`.
- **Rejected: resolving through `command -v crypt-env.exe` at run time.** It depends on `appendWindowsPath=true`, and that setting is commonly disabled.
- **Rejected: storing the path in `env.sh` and having the launcher read it.** That is one more coupling for no gain, since the launcher is regenerated on every Configure anyway.

### D3 — Launcher body

A fixed template in which the path is the only variable, emitted through the existing `sh_single_quote`:

```sh
#!/bin/sh
# >>> cryptenv managed launcher >>> — regenerated by CryptEnv Configure; removed by Remove.
exe='/mnt/d/Apps/CryptEnv/crypt-env.exe'
if [ ! -x "$exe" ]; then
  echo "crypt-env: Windows CLI not found at $exe — reinstall CryptEnv or re-run Settings → WSL Integration → Configure" >&2
  exit 127
fi
exec env -u CRYPTENV_API_URL -u CRYPTENV_CERT_PATH -u CRYPTENV_TOKEN_PATH "$exe" "$@"
```

- It is written atomically (temp file in the same directory, then `rename`) with mode `0755`.
- The marker line (second line) identifies a managed launcher. Write and remove refuse a pre-existing file that lacks the marker.
- `exec` keeps the PID/TTY and propagates the exit status. `env -u` covers the `WSLENV` forwarding case (spec: isolation). `env -u` is available in GNU coreutils and BusyBox.
- If interop is disabled, `exec` itself fails with a non-zero status and the shell's own error. That is acceptable: the spec only requires non-zero status with no fallback, and the `-x` pre-check covers the common "uninstalled" case with a clear message.

### D4 — Report and detection contract (backward compatible)

`ActionReport` gains:

```rust
#[serde(default)] pub launcher: Option<String>,        // in-distro path, when written/deleted
#[serde(default)] pub launcher_status: LauncherStatus, // written | unchanged | deleted | skipped | absent (default)
#[serde(default)] pub launcher_note: Option<String>,   // skip reason: "windows CLI not found" | "foreign file present"
```

`#[serde(default)]` keeps older helpers and newer GUIs (and the reverse) readable. The frontend `WslDistro` gains `launcher: boolean`, filled by a second fixed probe: `grep -q '>>> cryptenv managed launcher >>>' "$HOME/.local/share/cryptenv/bin/crypt-env"`. That probe is a separate constant with no interpolation, so `detect` stays read-only.

### D5 — `crypt-env setup wsl` (Linux CLI) unchanged

`apply` gains an `Option<&Path>` Windows-CLI parameter. The Linux subcommand passes `None`: it is itself a native binary, and installing a launcher would shadow nothing but still confuse. It still writes the `PATH` line into `env.sh`, which is harmless when the directory is absent.

## Security & Threat Model

- **Assets:** none secret. The launcher holds only a filesystem path. Secrets, token and cert stay under Windows ACLs and are used by the Windows CLI as before.
- **Injection:** the only caller-derived value (the Windows CLI path) goes through the argv vector (`wsl.exe … sh -c RUN_HELPER sh <helper> --windows-cli <path>`), never a shell string on the GUI side, and is single-quoted inside the generated script. There is a unit test with `'`, `$()`, spaces and backslashes in the path.
- **Clobbering / privilege:** writes happen only under `$HOME/.local/share/cryptenv/bin`, as the distro's default user (the same user the helper already runs as). Foreign files are never replaced (marker check). An atomic rename avoids a half-written executable.
- **PATH hijack:** appending (not prepending) means the launcher cannot shadow system or user binaries. An attacker able to write the owned directory already controls `$HOME`.
- **Environment leakage:** `CRYPTENV_*` variables are stripped before crossing into Windows, so WSL-side paths never redirect the Windows CLI's TLS anchor or token path.
- **Logs:** report fields are paths and enums only, consistent with the existing "no secret values" rule.

## Risks / Trade-offs

- [The Windows CLI sees the WSL working directory as `\\wsl.localhost\<distro>\...`, and absolute Linux path arguments are not translated] → Documented. Relative paths work. `.env`-writing commands should be checked manually on Windows (task 5.3).
- [Each call costs ~50–150 ms of interop overhead] → Acceptable for an interactive CLI. Users wanting native speed install a Linux build, which takes precedence by D1.
- [The TUI (`crypt-env tui`) through interop may render or handle keys differently] → Manual verification task. It is not blocked by spec.
- [Non-interactive shells that do not source `.bashrc` will not have the `PATH` entry] → Same limitation as the existing `env.sh`. The user can call the absolute launcher path from the report.
- [CryptEnv is moved or reinstalled elsewhere] → The launcher prints an actionable error and Reconfigure fixes it.
- [An old helper paired with a new GUI, or the reverse] → serde defaults; the missing launcher shows as "Reconfigure".

## Migration Plan

- Existing configured distros keep working unchanged. The panel shows "no `crypt-env` command → Reconfigure" until the user clicks it.
- Rollback: Remove deletes the launcher. Reverting the release leaves at most an inert `PATH` entry and launcher, both removed by Remove.
- Archive order: archive `windows-installer-cli-and-wsl-panel` first. This delta only adds requirements to the `wsl-integration` capability it introduces.
