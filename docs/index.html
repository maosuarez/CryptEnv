Encrypted local store

CryptEnv documentation

A local-first vault for API keys, credentials, links, notes and shell commands. Everything is encrypted on your device and reachable from a desktop app, a CLI, a terminal UI, an MCP server for AI agents and a localhost REST API.

The desktop app owns the vault: it holds the SQLite database, derives the key from your master password and serves an HTTPS API on 127.0.0.1:47821. Every other surface is a client of that API — none of them opens the database directly.

02Core concepts#

Items

Encrypted vault rows of type secret, credential, link, note or command. Each can carry categories.

Projects

A named group of environments tied to a root directory holding .crypt-env.yaml. Names are unique, case-insensitive.

Environments

e.g. local, staging, production. Each links vault items under env-var keys and has one or more .env output paths, relative to the project root or absolute.

Commands

Saved shell commands with {{VAR}} placeholders, resolved from arguments or the vault at run time.

An item is only "in" an environment when it is linked under a key (a real foreign key, not a name match). Linking happens when you add a variable, save the environment in the GUI, or import/receive items into it.

Environment names must match ^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$. Project names allow spaces and non-ASCII letters but reject path separators, control characters, reserved device names and leading/trailing dots or whitespace (max 128 chars).

Project root & .crypt-env.yaml#

Every project-aware command (config, add, fill, sync, inject, search, tui) finds .crypt-env.yaml by searching from the current directory upwards (like .git). Its directory is the project root. The file holds metadata only — never a secret value — and is meant to be committed.

.crypt-env.yaml
project:
  name: my-app
  description: Backend API
  categories:
  - backend
  environments:
  - name: default
    isDefault: true
    paths:
    - .env
  - name: production
    isDefault: false
    paths:
    - apps/api/.env.production
  • Environment paths relative to the root are resolved by the app at write time (they may not climb out of the root with ..); absolute paths are used as-is.
  • The environment is --env NAME, else the file's isDefault environment, else the vault's default.
  • The vault stores the root as the app sees it. A native Linux CLI inside WSL translates absolute paths to and from \\wsl.localhost\<distro>\… / C:\… automatically; CRYPTENV_PATH_TRANSLATION=off disables it.
  • A legacy crypt-env.json ({"project", "environment"}) is still read, with a notice to migrate via crypt-env init.

Global items#

Items marked global are reusable across projects (the GUI's Global Secrets view). Discovery surfaces — search, GET /items, GET /commands, the MCP list/search tools — union globals in by default and tag each row as linked, global or global+linked. Materialization surfaces — fill, inject, env example generation, LAN share — only ever use what is linked. Linking a global into an environment is always an explicit act.

Backup & restore#

Settings → Backup & Restore writes a .cenvbak file (format v2) containing every item (still as ciphertext), category, project (name, description, template, root path, categories), environment (name, default flag, paths), variable binding and item-ownership link. The organisational metadata is encrypted with your vault key inside the file, so project names, paths and variable keys are not readable without the master password. The MCP token and biometric enrollment are never included.

  • Replace needs the vault unlocked, the backup’s master password and your current master password. The restore is atomic: a complete replacement database is built and verified next to the live one and only then swapped in; if anything fails, the current vault is left untouched. The previous database is kept as vault.db.pre-restore until the next successful unlock.
  • Merge needs an unlocked vault and the backup’s master password. Items are re-encrypted with the current key; projects and environments that already exist (matched by name) are kept and missing ones are added. It also runs as a single all-or-nothing operation.
  • Older (v1) backups still restore items and categories. They carried no projects, so non-global items are placed in an auto-created Restored YYYY-MM-DD project and the restore summary says projects were not included. Items added through Import without a target go to an Imported YYYY-MM-DD project. These two projects are never reported as orphans.

04CLI reference#

crypt-env talks to the running app. The first authenticated command prompts for your master password (hidden input) and caches a session token. Commands marked 🔒 need a live session in the current terminal, like sudo: without one they ask for the master password (a wrong one aborts with no side effects). The session lasts the auto-lock timeout from Settings (default 5 min; "Never" still means 5 min here) and every command renews it, so a chain of commands asks once. Locking the vault ends every CLI session (a locked vault never renews one, and after the next unlock each terminal asks for the password again). Each terminal — Unix session + tty, or Windows console / Terminal tab (console host process + start time, so a recycled handle never inherits a session) — has its own session and token file (created 0600, atomically); other terminals prompt for their own and never log each other out. A 5xx, 429 or network error keeps the token; only a 401 discards it. eval "$(crypt-env inject X)" subshells count as the same terminal.

Project workflow#

crypt-env init [NAME] [--path PATH] [--yes]

Creates the vault project (or links an existing one with that name), records the current directory as its root and writes .crypt-env.yaml. NAME defaults to the folder name. --path sets the default environment's target: a directory (its .env) or a .env* file; default .env. An existing .crypt-env.yaml is never overwritten. If a project with that name is already bound to another directory, init fails (use config --relink); if it has no root yet, adopting this directory needs the same confirmation as config; with stdin not a terminal pass --yes (the session is still required).

shell
cd ~/code/my-service
crypt-env init                           # project "my-service", default env → .env
crypt-env init backend-api --path ./app  # default env → app/.env

crypt-env config [--relink] [--yes]

Compares the file's modification time with the vault's last change (project or any environment). File newer → the vault is updated (description, categories — created if missing —, environments and their paths, root). Vault newer → the file is regenerated. Vault environments missing from the file are kept (they may hold secrets) and reported.

Root binding: a project with a root belongs to that directory. From any other directory (for example a fresh clone) config and fill fail with project 'X' is bound to <root>, not this directory and change nothing; config --relink is the only way to move it, and always asks for confirmation. Consent: a push that changes the root or any environment's target paths prints a diff, needs a live session and a y/N answer (default no); with stdin not a terminal pass --yes. Metadata-only changes and brand-new projects need no confirmation.

Secrets & env files#

crypt-env add KEY=value | $VARNAME | FILE [--env NAME] [--global]

Adds secrets to the environment. If any key already exists there (or among global items with --global) nothing is added: Error: Key 'K' already exists in environment 'E'. Addition aborted. The CLI then offers to show the colliding value — only after y and the master password. If a key's request fails, the rest are still attempted; add then lists the keys added and failed (names only) and exits with status 2.

shell
crypt-env add "OPENAI_API_KEY=sk-..."
crypt-env add '$DATABASE_URL'
crypt-env add .env.local --env staging
crypt-env add "SHARED_AUTH_URL=https://auth.example" --global

crypt-env fill [--env NAME] 🔒

Writes every environment (or only --env) into its configured paths — the app does the writing, so WSL repos work with a Windows vault — and writes/extends a keys-only .env.example next to each target. A pre-existing file not created by CryptEnv is backed up to <path>.bak first. .env.example goes next to each .env actually written. A symlink target is refused (TARGET_SYMLINK, nothing written) and a relative path may not leave the project root through a symlinked directory.

crypt-env sync [--global] [--env NAME] [--example PATH] 🔒

Reads .env.example (current directory, then the project root) and creates each key missing from the environment with the value change-me. With --global, keys matching a global secret are linked to it instead and the environment is then written to its .env target(s).

crypt-env inject KEY... [--env NAME] [--shell pwsh|bash|zsh|sh] 🔒

Prints single-quoted assignments on stdout only; the password prompt goes to the terminal. All keys are resolved before anything is printed. Keys must match ^[A-Za-z_][A-Za-z0-9_]*$ or the command fails with nothing on stdout. Values are quoted so they never execute: PowerShell doubles all five single-quote characters (' and U+2018–U+201B); bash/zsh use '\'', or $'...' when the value has a line break; --shell sh refuses values with a newline. The GUI “Copy as bash / PowerShell” produces the same text.

shell
# bash / zsh
eval "$(crypt-env inject DATABASE_URL API_KEY)"
# PowerShell
crypt-env inject DATABASE_URL --shell pwsh | Invoke-Expression

crypt-env search [PATTERN] [--global] 🔒

Prints KEY, ENVIRONMENT, TYPE, SCOPE for the project's variables across environments, or global items with --global. %TEXT is a substring match; anything else is a case-insensitive regex.

shell
crypt-env search %TOKEN
crypt-env search '^DB_'
crypt-env search --global

06MCP server#

crypt-env-mcp is a Model Context Protocol server (JSON-RPC 2.0 over stdio) that lets AI assistants such as Claude Code, Claude Desktop or Cursor work with your vault. It is designed so the model can use secrets without seeing them: values are written to files or injected into processes, never returned in tool responses.

Setup#

  1. Open CryptEnv → Settings → Integrations → generate an MCP token. It is stored in the app data folder as mcp_token.
  2. Keep the app running and unlocked.
  3. Register the server in your MCP client and restart it. It is a stdio command — do not configure a url.
claude_desktop_config.json
{
  "mcpServers": {
    "cryptenv": {
      "command": "C:\\full\\path\\to\\crypt-env-mcp.exe"
    }
  }
}
claude code
claude mcp add cryptenv -- crypt-env-mcp

On Windows the installer puts crypt-env-mcp.exe on your PATH; use where crypt-env-mcp to get the absolute path if your client needs one.

MCP safeguards#

The MCP token never reads secret values. The server tells the MCP token apart from your own session and enforces this on every route.

  • Reserved for you (403 MCP_FORBIDDEN): revealing a value, confirming a LAN pairing fingerprint, changing auto_lock_timeout, writing files outside a project's root, overwriting a file CryptEnv does not manage, returning filled content inline, and project/environment structure changes.
  • Needs your approval: relay_send, share_export, generate_env and add/update/delete_mcp_server. The app shows a modal naming the operation, the items and the destination (Deny is focused by default) and brings the window forward. The agent gets pending_approval and an approvalId and polls crypt_env_approval_status. A request expires after 120 s, at most 8 are pending (429 APPROVALS_FULL), and locking the vault discards them. The relay code, passphrase and export passphrase are shown only in the app, never returned to the agent.
  • crypt_env_run_command runs inside the app: the child starts from an empty environment (a fixed baseline such as PATH, HOME, SystemRoot, TEMP, LANG, plus the keys you selected with crypt_env_inject_env); stdin is empty; every {{param}} value must match [A-Za-z0-9._/:@=+,-]{0,256} (no spaces or shell metacharacters, otherwise nothing runs); injected values and their base64 and hex forms are replaced by [REDACTED:KEY] in the output; each stream is capped at 64 KiB captured and 2000 characters returned; the whole process tree is killed after 120 s, on vault lock, or when the MCP session ends (Unix process group, Windows Job Object). At most 4 commands run at once (429 EXEC_BUSY beyond a queue of 8). Values shorter than 4 characters are not redacted, and a command that transforms a secret (for example rev) before printing it can defeat redaction.
  • WSL: when the MCP client runs in WSL and the app on Windows, the app runs the command in the client's distribution with wsl.exe -d <distro> --cd <dir> --exec. Secrets travel over stdin, never on the command line or in WSLENV.
  • Generated files: crypt_env_generate_env writes to a private directory inside the app data folder (mode 0700, files 0600), not to the shared temp directory. They are deleted after 10 minutes, when the vault locks and at app exit; leftovers are swept at startup.
  • MCP host config: the app, not the MCP process, writes claude_desktop_config.json and .claude/mcp_servers.json, so the approval cannot be bypassed. With WSL, the global config written is the one on the app's side (Windows).

Breaking for agents. relay_send, share_export, generate_env and the MCP-server tools now return pending_approval instead of a result; crypt_env_share_confirm and auto_lock_timeout in update_settings are gone; run_command rejects parameters with spaces or shell metacharacters; crypt_env_inject_env no longer sets the MCP process environment.

Whole-project relay sharing has no MCP tool on purpose: it needs the sender's explicit consent in the GUI or CLI.

07REST API#

The app serves HTTPS on https://127.0.0.1:47821, bound to loopback only. The CLI, TUI and MCP server are built on it; you can call it from your own scripts too. Errors come back as {"error": "...", "code": "..."}. Internal failures return 500 with {"error": "internal error", "code": "INTERNAL_ERROR", "id": "a1b2c3d4"}: no SQL, schema or file paths are exposed, and the detail is written to the app's local log under the same id.

Auth & TLS#

  • TLS: a self-signed certificate is generated on first launch at <app data>/com.maosuarez.cryptenv/tls/cert.pem. Pass --cacert with that file (or -k for quick tests). At every start the app checks that the certificate and key match and that the certificate is not about to expire, and regenerates them if not; the published cert.pem path stays the same.
  • Token: send X-Vault-Token with either a session token from POST /unlock (expires) or the static MCP token from Settings.
  • The static MCP token is a separate principal: every route is allowed, denied (403 MCP_FORBIDDEN) or approval-gated for it (see MCP safeguards). Unclassified routes are denied.
  • Tokens are compared in constant time. Only wrong master passwords on /unlock are throttled: after a failure the next attempt must wait 1 s, doubling per consecutive failure up to 60 s (429 RATE_LIMITED with Retry-After); a correct password resets it. The desktop unlock shares the same counter. Malformed requests are rejected with 4xx and never count, so another local process cannot lock you out.

Internet relay (Supabase SQL v2)#

The relay is your own Supabase project. Single use and the 24-hour expiry are enforced by the database, not by the client: the table has no access for the anon key, and every operation goes through two SECURITY DEFINER functions. A package can be claimed once (the claim deletes it), expired packages are never returned and are purged on every relay call, and only a hash of the code is stored. Payloads are capped at 1 MiB and stay encrypted client-side.

Breaking change. Earlier versions used a permissive relay_packages table that did not enforce either guarantee. Send and receive now fail with RELAY_SCHEMA_OUTDATED until you apply the SQL below. In-flight shares on the old table are not migrated: re-share after upgrading.

  1. Open Settings → Internet Sharing → Custom relay → Setup SQL (or copy the block below) and run it in the Supabase SQL Editor.
  2. Click Check schema in the same panel; it reports whether v2 is detected.
  3. Optional cleanup of the old table: drop table relay_packages;
sql
create table if not exists relay_packages_v2 (
  code_hash  text primary key,
  payload    text not null check (octet_length(payload) <= 1048576),
  expires_at timestamptz not null default now() + interval '24 hours'
);
alter table relay_packages_v2 enable row level security;
revoke all on relay_packages_v2 from anon, authenticated;

create or replace function relay_put(p_code_hash text, p_payload text) returns void
language plpgsql security definer set search_path = public as $$
begin
  delete from relay_packages_v2 where expires_at < now();
  insert into relay_packages_v2(code_hash, payload) values (p_code_hash, p_payload);
end $$;

create or replace function relay_claim(p_code_hash text) returns text
language plpgsql security definer set search_path = public as $$
declare v text;
begin
  delete from relay_packages_v2 where expires_at < now();
  delete from relay_packages_v2 where code_hash = p_code_hash returning payload into v;
  return v;
end $$;

create or replace function relay_schema_version() returns int language sql as $$ select 2 $$;
grant execute on function relay_put(text,text), relay_claim(text), relay_schema_version() to anon;

Notes: whoever guesses a live code can claim it first, which burns the package (it is still encrypted with the passphrase); the receiver sees "code not found or already used" and the sender re-shares. A wrong passphrase also consumes the package. All relay calls time out after 10 s to connect and 30 s total, and at most two Argon2id derivations run at once.

Write-target gating#

Files written by /fill, /environments/:id/inject and /environments/:id/example start with a marker line:

.env
# crypt-env: managed file (project: my-app, environment: production)
  • An existing file without the marker is foreign. Writing to it via output_path/output_dir returns 409 TARGET_EXISTS unless overwrite: true.
  • With overwrite: true the old content is copied to <path>.bak first (409 BACKUP_EXISTS if a backup is already there).
  • Paths configured on the environment itself are always written through, with the same backup, and reported in unmanagedPaths. Relative configured paths resolve against the project's rootPath and may not leave it; a relative path on a project without a root is an error.
  • Names derived from output_dir are contained to that directory (422 PATH_NOT_CONTAINED otherwise).
  • A target whose final component is a symlink (or Windows reparse point) is refused with 409 TARGET_SYMLINK; nothing is written and no .bak is made.
  • A target that exists but is not a regular file (device, FIFO, socket, directory) is refused with 409 NOT_REGULAR_FILE without being read. An existing target is read for classification up to 1 MiB; a larger file counts as foreign.
  • Writes are atomic: content goes to a .cenv-* temp file in the same directory (mode 0600 on Unix), is flushed, then renamed over the target. A failed write leaves the previous file intact and no temp file behind.

Value quoting#

Each variable is written as one KEY=VALUE line that common dotenv parsers read back exactly:

  • Values made only of A-Za-z0-9_./:@+,=- are written bare.
  • Other values without a newline, carriage return or ' are single-quoted (literal).
  • Everything else (multi-line values such as PEM keys, values containing ') is double-quoted with \\, \", \$, \n and \r escaped.
  • Keys must match ^[A-Za-z_][A-Za-z0-9_.]*$; other keys are not written. Inject also decrypts only the items the environment references. Keys that were not written (undecryptable item or invalid name) are listed by name in failedKeys of the inject response; the other keys are still written. crypt-env fill prints them.
  • Single-quoted and bare values also work with source in bash; double-quoted escapes are understood by python-dotenv and Node dotenv, not by the shell. Node dotenv does not unescape \$.

Add *.bak to .gitignore wherever CryptEnv writes.

Examples#

bash
CERT="$HOME/.local/share/com.maosuarez.cryptenv/tls/cert.pem"   # Windows: %APPDATA%\com.maosuarez.cryptenv\tls\cert.pem
API=https://127.0.0.1:47821

# Unlock → session token
TOKEN=$(curl -s --cacert "$CERT" -X POST $API/unlock \
  -H 'Content-Type: application/json' \
  -d '{"master_password": "..."}' | jq -r .token)

# List items in a project/environment
curl -s --cacert "$CERT" "$API/items?project=my-app&environment=production" \
  -H "X-Vault-Token: $TOKEN"

# Create an item linked as DB_HOST
curl -s --cacert "$CERT" -X POST "$API/items?environment_id=1" \
  -H "X-Vault-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"type": "secret", "name": "DB_HOST", "value": "localhost", "key": "DB_HOST"}'

# Fill a template into a file
curl -s --cacert "$CERT" -X POST "$API/fill?project=my-app&environment=production" \
  -H "X-Vault-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"template": "DB_HOST=\nPORT=3000\n", "output_path": "/abs/path/.env"}'

# Write an environment to its configured paths
curl -s --cacert "$CERT" -X POST $API/environments/1/inject \
  -H "X-Vault-Token: $TOKEN" -H 'Content-Type: application/json' -d '{}'

Full contract, edge cases and known limitations: docs/reference.md.

08Security model#

Encryption at rest

Each item is encrypted with AES-256-GCM using a key derived from your master password with Argon2id. Deletes are zeroed on disk (secure_delete).

Volatile keys

The master password and derived key live in memory only while unlocked and are zeroized on lock. Auto-lock after a configurable timeout.

Local-only API

Loopback binding, TLS, token auth with constant-time comparison, rate-limited unlock.

LAN sharing

The 6-digit pairing code feeds a SPAKE2 key exchange, so only a peer that knows it can derive the session key; mDNS advertises only a random session id and a protocol version, never anything derived from the code. Both sides prove the key (key confirmation) before any item moves, then compare a 64-bit fingerprint (XXXX-XXXX-XXXX-XXXX) and confirm in the desktop app. Sockets time out after 30 s (handshake 60 s), 3 wrong-code attempts abort the session, only one session runs at a time, and locking the vault or closing the dialog cancels it. Both devices must run the same version: v1.0.6 peers are rejected with an “update the other device” message.

No plaintext leaks

Values never appear in logs, errors or list responses. Reveal requires an explicit confirm and is refused to the MCP token; commands run inside the app and their output is redacted. Relay codes and passphrases reach only you, through an approval in the app.

Clipboard hygiene

Secrets copied from the desktop app are cleared from the clipboard after 30 seconds and immediately on lock, unless you copied something else meanwhile. On Windows they are excluded from clipboard history (Win+V) and cloud sync. Third-party clipboard managers that ignore these flags may still capture them. Locking also closes any open command, setup or token dialog.

Report vulnerabilities privately as described in SECURITY.md.
