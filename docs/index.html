Encrypted local store

CryptEnv documentation

A local-first vault for API keys, credentials, links, notes and shell commands. Everything is encrypted on your device and reachable from a desktop app, a CLI, a terminal UI, an MCP server for AI agents and a localhost REST API.

Download latest release CLI reference MCP setup
AES-256-GCMArgon2id127.0.0.1 onlyTauri 2 · RustMIT

The desktop app owns the vault: it holds the SQLite database, derives the key from your master password and serves an HTTPS API on 127.0.0.1:47821. Every other surface is a client of that API — none of them opens the database directly.

02Core concepts#

Items

Encrypted vault rows of type secret, credential, link, note or command. Each can carry categories.

Projects

A named group of environments tied to a root directory holding .crypt-env.yaml. Names are unique, case-insensitive.

Environments

e.g. local, staging, production. Each links vault items under env-var keys and has one or more .env output paths, relative to the project root or absolute.

Commands

Saved shell commands with {{VAR}} placeholders, resolved from arguments or the vault at run time.

An item is only "in" an environment when it is linked under a key (a real foreign key, not a name match). Linking happens when you add a variable, save the environment in the GUI, or import/receive items into it.

Environment names must match ^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$. Project names allow spaces and non-ASCII letters but reject path separators, control characters, reserved device names and leading/trailing dots or whitespace (max 128 chars).

Project root & .crypt-env.yaml#

Every project-aware command (config, add, fill, sync, inject, search, tui) finds .crypt-env.yaml by searching from the current directory upwards (like .git). Its directory is the project root. The file holds metadata only — never a secret value — and is meant to be committed.

.crypt-env.yaml
project:
  name: my-app
  description: Backend API
  categories:
  - backend
  environments:
  - name: default
    isDefault: true
    paths:
    - .env
  - name: production
    isDefault: false
    paths:
    - apps/api/.env.production
  • Environment paths relative to the root are resolved by the app at write time (they may not climb out of the root with ..); absolute paths are used as-is.
  • The environment is --env NAME, else the file's isDefault environment, else the vault's default.
  • The vault stores the root as the app sees it. A native Linux CLI inside WSL translates absolute paths to and from \\wsl.localhost\<distro>\… / C:\… automatically; CRYPTENV_PATH_TRANSLATION=off disables it.
  • A legacy crypt-env.json ({"project", "environment"}) is still read, with a notice to migrate via crypt-env init.

Global items#

Items marked global are reusable across projects (the GUI's Global Secrets view). Discovery surfaces — search, GET /items, GET /commands, the MCP list/search tools — union globals in by default and tag each row as linked, global or global+linked. Materialization surfaces — fill, inject, env example generation, LAN share — only ever use what is linked. Linking a global into an environment is always an explicit act.

The CLI, TUI and MCP server read these optional environment variables. The defaults work when client and app run on the same machine; overrides exist for split setups such as WSL ↔ Windows.

04CLI reference#

crypt-env talks to the running app. The first authenticated command prompts for your master password (hidden input) and caches a session token. Commands marked 🔒 need a live session in the current terminal, like sudo: without one they ask for the master password (a wrong one aborts with no side effects). The session lasts the auto-lock timeout from Settings (default 5 min; "Never" still means 5 min here) and every command renews it, so a chain of commands asks once. Each terminal — Unix session + tty, or Windows console / Terminal tab — has its own session and token file; other terminals prompt for their own and never log each other out. eval "$(crypt-env inject X)" subshells count as the same terminal.

CommandPurpose
init [NAME] [--path PATH]Register this directory as a project root and write .crypt-env.yaml
configSync .crypt-env.yaml ⇄ vault (last modified wins)
addAdd secrets from KEY=value, $VARNAME or a .env file; halts on collisions
fill 🔒Write each environment's target files plus .env.example
sync 🔒Provision keys from .env.example into the vault
inject 🔒Print shell assignments for eval
search 🔒List variable names and metadata (never values)
doctorDiagnostics
setup wsl [DISTRO]Configure the WSL ↔ Windows split
tuiInteractive terminal UI

memory, list, exec, cmd, project, share, relay, category and set were removed from the CLI (unrecognized subcommand). Sharing, saved commands, categories and project deletion remain in the GUI; use inject instead of set.

Project workflow#

crypt-env init [NAME] [--path PATH]

Creates the vault project (or links an existing one with that name), records the current directory as its root and writes .crypt-env.yaml. NAME defaults to the folder name. --path sets the default environment's target: a directory (its .env) or a .env* file; default .env. An existing .crypt-env.yaml is never overwritten.

shell
cd ~/code/my-service
crypt-env init                           # project "my-service", default env → .env
crypt-env init backend-api --path ./app  # default env → app/.env

crypt-env config

Compares the file's modification time with the vault's last change (project or any environment). File newer → the vault is updated (description, categories — created if missing —, environments and their paths, root). Vault newer → the file is regenerated. Vault environments missing from the file are kept (they may hold secrets) and reported.

Secrets & env files#

crypt-env add KEY=value | $VARNAME | FILE [--env NAME] [--global]

Adds secrets to the environment. If any key already exists there (or among global items with --global) nothing is added: Error: Key 'K' already exists in environment 'E'. Addition aborted. The CLI then offers to show the colliding value — only after y and the master password.

shell
crypt-env add "OPENAI_API_KEY=sk-..."
crypt-env add '$DATABASE_URL'
crypt-env add .env.local --env staging
crypt-env add "SHARED_AUTH_URL=https://auth.example" --global

crypt-env fill [--env NAME] 🔒

Writes every environment (or only --env) into its configured paths — the app does the writing, so WSL repos work with a Windows vault — and writes/extends a keys-only .env.example next to each target. A pre-existing file not created by CryptEnv is backed up to <path>.bak first.

crypt-env sync [--global] [--env NAME] [--example PATH] 🔒

Reads .env.example (current directory, then the project root) and creates each key missing from the environment with the value change-me. With --global, keys matching a global secret are linked to it instead and the environment is then written to its .env target(s).

crypt-env inject KEY... [--env NAME] [--shell pwsh|bash|zsh|sh] 🔒

Prints single-quoted assignments on stdout only; the password prompt goes to the terminal. All keys are resolved before anything is printed.

shell
# bash / zsh
eval "$(crypt-env inject DATABASE_URL API_KEY)"
# PowerShell
crypt-env inject DATABASE_URL --shell pwsh | Invoke-Expression

crypt-env search [PATTERN] [--global] 🔒

Prints KEY, ENVIRONMENT, TYPE, SCOPE for the project's variables across environments, or global items with --global. %TEXT is a substring match; anything else is a case-insensitive regex.

shell
crypt-env search %TOKEN
crypt-env search '^DB_'
crypt-env search --global

Setup & doctor#

crypt-env setup wsl [DISTRO] [--cert-path PATH] [--api-url URL] [--remove]

Inside WSL: detects the distribution and writes ~/.config/cryptenv/env.sh plus a marked block in your shell rc (one-time backup). --cert-path is required when the Windows APPDATA isn't forwarded. On Windows: lists installed distributions (or reports none); run crypt-env setup wsl <distro> to configure one through the bundled helper. --remove undoes it.

shell
crypt-env setup wsl                # inside WSL, or list distros on Windows
crypt-env setup wsl Ubuntu         # from Windows

crypt-env doctor

Reports the app/health endpoint, vault lock state, TLS certificate (path and days to expiry), CLI session token (and whether its file is readable by others), MCP token, .crypt-env.yaml validity and WSL status.

06MCP server#

crypt-env-mcp is a Model Context Protocol server (JSON-RPC 2.0 over stdio) that lets AI assistants such as Claude Code, Claude Desktop or Cursor work with your vault. It is designed so the model can use secrets without seeing them: values are written to files or injected into processes, never returned in tool responses.

Setup#

  1. Open CryptEnv → Settings → Integrations → generate an MCP token. It is stored in the app data folder as mcp_token.
  2. Keep the app running and unlocked.
  3. Register the server in your MCP client and restart it. It is a stdio command — do not configure a url.
claude_desktop_config.json
{
  "mcpServers": {
    "cryptenv": {
      "command": "C:\\full\\path\\to\\crypt-env-mcp.exe"
    }
  }
}
claude code
claude mcp add cryptenv -- crypt-env-mcp

On Windows the installer puts crypt-env-mcp.exe on your PATH; use where crypt-env-mcp to get the absolute path if your client needs one.

07REST API#

The app serves HTTPS on https://127.0.0.1:47821, bound to loopback only. The CLI, TUI and MCP server are built on it; you can call it from your own scripts too. Errors come back as {"error": "...", "code": "..."}.

Auth & TLS#

  • TLS: a self-signed certificate is generated on first launch at <app data>/com.maosuarez.cryptenv/tls/cert.pem. Pass --cacert with that file (or -k for quick tests).
  • Token: send X-Vault-Token with either a session token from POST /unlock (expires) or the static MCP token from Settings.
  • Tokens are compared in constant time. /unlock is rate-limited to 5 attempts per 60 s (429 RATE_LIMITED with Retry-After).

Write-target gating#

Files written by /fill, /environments/:id/inject and /environments/:id/example start with a marker line:

.env
# crypt-env: managed file (project: my-app, environment: production)
  • An existing file without the marker is foreign. Writing to it via output_path/output_dir returns 409 TARGET_EXISTS unless overwrite: true.
  • With overwrite: true the old content is copied to <path>.bak first (409 BACKUP_EXISTS if a backup is already there).
  • Paths configured on the environment itself are always written through, with the same backup, and reported in unmanagedPaths. Relative configured paths resolve against the project's rootPath and may not leave it; a relative path on a project without a root is an error.
  • Names derived from output_dir are contained to that directory (422 PATH_NOT_CONTAINED otherwise).

Add *.bak to .gitignore wherever CryptEnv writes.

Examples#

bash
CERT="$HOME/.local/share/com.maosuarez.cryptenv/tls/cert.pem"   # Windows: %APPDATA%\com.maosuarez.cryptenv\tls\cert.pem
API=https://127.0.0.1:47821

# Unlock → session token
TOKEN=$(curl -s --cacert "$CERT" -X POST $API/unlock \
  -H 'Content-Type: application/json' \
  -d '{"master_password": "..."}' | jq -r .token)

# List items in a project/environment
curl -s --cacert "$CERT" "$API/items?project=my-app&environment=production" \
  -H "X-Vault-Token: $TOKEN"

# Create an item linked as DB_HOST
curl -s --cacert "$CERT" -X POST "$API/items?environment_id=1" \
  -H "X-Vault-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"type": "secret", "name": "DB_HOST", "value": "localhost", "key": "DB_HOST"}'

# Fill a template into a file
curl -s --cacert "$CERT" -X POST "$API/fill?project=my-app&environment=production" \
  -H "X-Vault-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"template": "DB_HOST=\nPORT=3000\n", "output_path": "/abs/path/.env"}'

# Write an environment to its configured paths
curl -s --cacert "$CERT" -X POST $API/environments/1/inject \
  -H "X-Vault-Token: $TOKEN" -H 'Content-Type: application/json' -d '{}'

Full contract, edge cases and known limitations: docs/reference.md.

08Security model#

Encryption at rest

Each item is encrypted with AES-256-GCM using a key derived from your master password with Argon2id. Deletes are zeroed on disk (secure_delete).

Volatile keys

The master password and derived key live in memory only while unlocked and are zeroized on lock. Auto-lock after a configurable timeout.

Local-only API

Loopback binding, TLS, token auth with constant-time comparison, rate-limited unlock.

LAN sharing

The 6-digit pairing code feeds a SPAKE2 key exchange, so only a peer that knows it can derive the session key; mDNS advertises only a random session id and a protocol version, never anything derived from the code. Both sides prove the key (key confirmation) before any item moves, then compare a 64-bit fingerprint (XXXX-XXXX-XXXX-XXXX) and confirm in the desktop app. Sockets time out after 30 s (handshake 60 s), 3 wrong-code attempts abort the session, only one session runs at a time, and locking the vault or closing the dialog cancels it. Both devices must run the same version: v1.0.6 peers are rejected with an “update the other device” message.

No plaintext leaks

Values never appear in logs, errors or list responses. Reveal requires an explicit confirm; the MCP server writes or injects instead of returning.

Report vulnerabilities privately as described in SECURITY.md.
